# 001_cli: Phase 1 Web Server Implementation

## Overview

The `001_cli` integration test validates that the Forge CLI can serve a minimal web application. This represents **Phase 1** of the Forge framework: "Skeleton and one route (no DB/auth/templates yet)".

## Goals

- CLI can detect and serve Forge projects with `forge dev` (development) or `forge serve` (production)
- Minimal web server that "does nothing" (serves basic responses)
- Strict project structure requirements like Django/Rails
- Fail fast with helpful error messages when requirements not met

## Architecture Decisions

### 1. Project Detection: Strict Structure

**Decision**: Require explicit Forge project structure, fail fast with suggestions.

**Detection Logic**:
- Look for `Cargo.toml` in current directory
- Verify `forge` dependency exists in `Cargo.toml`
- Require `src/main.rs` that uses `forge::App`
- If any component missing → clear error with `forge new` suggestion

**Rationale**:
- Like Django/Rails: clear project boundaries
- Project generator (`forge new`) creates correct structure
- Not responsible for incomplete/malformed projects
- Easier implementation and debugging

### 2. CLI Commands: Start with `serve`

**Current**: Only `--version` flag
**Phase 1**: Add `serve` subcommand
**Future**: Add `dev` (auto-reload), `new`, `generate`, `migrate`

**Command Structure** (current):
```bash
forge dev            # Development: backend + Vite dev server; open http://localhost:3000
forge serve          # Production: build frontend, then serve static assets
forge new myapp      # Create new project
forge --version      # Version info
```

### 3. Error Handling: Fail Fast with Help

**Option C Chosen**: Clear error messages with actionable suggestions

**Examples**:
```bash
$ cd empty_dir && forge serve
Error: No Cargo.toml found. Run `forge new myapp` to create a Forge project.

$ cd rust_project_without_forge && forge serve
Error: forge dependency not found in Cargo.toml. Add `forge = { path = "../forge" }` to dependencies.

$ cd forge_project_without_main && forge serve
Error: src/main.rs not found. Ensure your project has a main.rs that uses forge::App.
```

### 4. Web Server: Minimal Axum Application

**"Does nothing" means**:
- Starts HTTP server on configurable port (default 3000)
- Serves single route: `GET /` returns "Hello from Forge!"
- No database, no auth, no templates
- Clean shutdown on Ctrl+C

**Minimal Forge App Structure**:
```rust
// src/main.rs
use forge::App;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
  App::new()
      .route("/", || async { "Hello from Forge!" })
      .serve()
      .await
}
```

## Implementation Plan

### Phase 1A: Core Library (`crates/forge/`)

**Dependencies to Add**:
```toml
# Cargo.toml
[dependencies]
axum = "0.7"
tokio = { version = "1", features = ["full"] }
tower = "0.4"
tower-http = "0.5"
tracing = "0.1"
tracing-subscriber = { version = "0.3", features = ["env-filter"] }
```

**Core API** (`src/lib.rs`):
```rust
pub mod app;
pub mod error;

pub use app::App;
pub use error::Error;
```

**App Builder** (`src/app.rs`):
- `App::new()` constructor
- `.route(path, handler)` for adding routes
- `.serve()` to start server with graceful shutdown
- Internal Axum router management

**Error Types** (`src/error.rs`):
- Custom error enum for Forge-specific errors
- `thiserror` for ergonomic error handling

### Phase 1B: CLI Enhancement (`crates/forge-cli/`)

**Add `clap` subcommands**:
```rust
#[derive(Parser)]
#[command(name = "forge")]
enum Commands {
  Serve {
      #[arg(short, long, default_value = "3000")]
      port: u16,
  },
  #[command(skip)]  // Keep version as top-level flag
  Version,
}
```

**Project Detection Logic**:
- Check for `Cargo.toml` existence
- Parse TOML to verify forge dependency
- Check for `src/main.rs`
- Return `Result<(), Error>` with helpful messages

**Serve Command Flow**:
1. Detect project structure
2. If valid → spawn `cargo run` in background
3. Forward signals for clean shutdown
4. Display server URL and status

### Phase 1C: Test Implementation (`test/001_cli/`)

**Test Directory Structure**:
```
test/001_cli/
├── Cargo.toml          # Forge app with minimal dependencies
├── src/
│   └── main.rs         # Minimal app using forge::App

```

**Test Cases** (`crates/forge-cli/tests/001_cli.rs`):

- Server responds on configured port
- `GET /` returns expected response
- Clean shutdown on termination
- Error cases: missing Cargo.toml, missing forge dep, etc.

## Dependencies & Ecosystem

### Core Runtime Stack
- **axum**: Type-safe web framework with extractors
- **tokio**: Async runtime for async/await
- **tower**: Middleware framework for composability
- **tower-http**: Additional HTTP utilities (CORS, compression, etc.)
- **tracing**: Structured logging framework
- **tracing-subscriber**: Log formatting and filtering

### CLI & Tooling
- **clap**: Command-line argument parsing with derive macros
- **cargo_metadata**: For parsing Cargo.toml programmatically
- **tokio::process**: For spawning `cargo run` subprocess

### Testing
- **assert_cmd**: For testing CLI binaries
- **reqwest**: For testing HTTP responses in integration tests
- **tokio::test**: For async test functions

## Safety & Performance Considerations

### Memory Safety (Rust Guarantees)
- Ownership system prevents use-after-free/data races
- RAII ensures resources cleaned up
- No manual memory management required

### Async Safety Patterns
- Tokio's work-stealing scheduler for efficient task execution
- Structured concurrency with `JoinHandle` for proper cleanup
- Channel-based communication between CLI and server process

### Error Handling Strategy
- Result types for recoverable errors
- Custom error types with `thiserror` for context
- Graceful degradation where possible
- Clear error messages for user actionability

## Testing Strategy

### Integration Tests

- Error message formatting

### Property-Based Tests (Future)

## Success Criteria

**Functional**:
- `forge serve` in valid project starts server
- Server responds to `GET /` with "Hello from Forge!"
- Server runs on specified port
- Clean shutdown on SIGTERM/SIGINT

**User Experience**:
- Clear error messages for invalid projects
- Helpful suggestions (`forge new myapp`)
- Minimal configuration required
- Fast startup time (< 2 seconds)

**Code Quality**:
- Comprehensive test coverage
- Proper error handling throughout
- Memory-safe implementation
- Async patterns following Tokio best practices

### Breaking Changes in Phase 2 (002_config)

**Note**: Phase 2 (002_config) will introduce significant breaking changes related to configuration management.

-   The `--port` flag for `forge serve` will be removed. The port will now be determined by the `config/app.toml` file.
-   Configuration loading will become automatic within `App::new()`, simplifying application setup.
-   The `forge new` command will be introduced to generate new Forge projects with the correct configuration structure, replacing manual project setup.
