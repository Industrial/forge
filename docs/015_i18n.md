# Internationalization (i18n)

Forge recommends the **Fluent** localization stack for message translation and the **accept-language** crate for resolving the user’s locale from HTTP requests. This gives request-scoped, explicit locale handling suitable for async Axum handlers.

## Objectives

1. **Message translation:** Resolve message keys to localized strings with arguments and pluralization.
2. **Locale resolution:** Derive locale from `Accept-Language`, cookie, or route and use it per request.
3. **No global state:** Pass locale and loader explicitly so it works correctly with async and spawning.
4. **Standard format:** Use Fluent (FTL) so tooling and translators can work with a well-supported format.

## Recommended crates

| Role | Crate | Purpose |
|------|--------|--------|
| **Messages** | **fluent** | Core Fluent types: `FluentBundle`, `FluentResource`, `FluentArgs`. |
| **Loader API** | **fluent-templates** | High-level loader: `StaticLoader` (compile-time) or `ArcLoader` (runtime); `lookup(locale, key, args)`. |
| **Locale from request** | **accept-language** | Parse `Accept-Language` and pick best match from supported locales (highest-starred among focused locale-parsing crates). |

Optional: **unic-langid** or **rustfmt-bindings** for `LanguageIdentifier` if you need a standard type for locale tags (e.g. `en-US`, `de`). Fluent and fluent-templates work with locale strings.

## When to use which loader

- **StaticLoader** (macro): Embed FTL files in the binary at compile time. Best for production apps that ship a fixed set of locales.
- **ArcLoader**: Load FTL at runtime; support hot-reload or dynamic locale files. Useful for development or admin-loaded translations.

## File layout

Place Fluent (`.ftl`) files under a `locales` directory, one subdirectory per locale:

```
locales/
  en-US/
    main.ftl    # or app.ftl, messages.ftl
  de/
    main.ftl
  fr/
    main.ftl
```

Example `locales/en-US/main.ftl`:

```
greeting = Hello, { $name }!
items-count = { $count ->
  [0]     No items
  [one]   One item
  *[other] { $count } items
}
```

## Resolving locale (Accept-Language)

Use **accept-language** to parse the header and choose the best supported locale:

```rust
use accept_language::intersection;

// In middleware or extractor: read Accept-Language from headers,
// then intersection(header_value, &["en-US", "de", "fr"]) to get
// the first matching locale. Use a fallback (e.g. "en-US") if empty.
```

Store the chosen locale in request extensions or state so handlers can use it. Optionally allow override via cookie or query (e.g. `?lang=de`) and prefer that over the header when present.

## Using translations in handlers

1. **State:** Put the loader (e.g. `Arc<StaticLoader>`) in Axum app state so handlers can access it.
2. **Locale:** Get the resolved locale (e.g. `Extension(locale)` or from state) in each handler.
3. **Lookup:** Call `loader.lookup(&locale, "key", args)` or `lookup_with_args` (fluent-templates). Handle missing messages with a fallback locale or the key.

No global or thread-local locale: every lookup is explicit with `(loader, locale, key, args)`.

## Pluralization and arguments

Fluent handles plurals and selectors in FTL (e.g. `[one]` / `*[other]`). Pass arguments as `FluentArgs` or the map type your loader expects (e.g. `[("name", "World"), ("count", 2)]`). fluent-templates’ `lookup_with_args` (or equivalent) accepts these and runs Fluent’s formatter.

## Integration with Forge

- **No framework dependency:** Forge does not depend on fluent or accept-language. Applications add these crates and wire them as above.
- **Pattern:** Middleware or extractor that uses accept-language → set locale in extensions; router with state containing the loader; handlers that take State and locale and call `loader.lookup(...)`.
- **Future:** Forge may provide a thin helper (e.g. `forge::i18n::translate(loader, locale, key, args)`) or re-export a recommended extractor; the design stays “explicit locale + loader.”

## Status

- **Scaffold:** `forge new` generates `locales/en-US/main.ftl`, `locales/de/main.ftl`, app deps (`fluent`, `fluent-templates`, `accept-language`, `unic-langid`), a static `LOCALES` loader, and GET `/` (root) handled by the i18n handler that resolves locale from `Accept-Language` and returns the localized greeting.
- **E2E:** `test/e2e/015_i18n.rs` asserts layout (locales present), GET `/` with `Accept-Language: en-US` → body contains "Hello" and "World", with `Accept-Language: de` → "Hallo" and "World", and without header → fallback "Hello".
- **Framework:** Forge still does not depend on i18n crates; apps add and wire them as above.
